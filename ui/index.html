Required schema and recommended content

Cascade's current taxonomy requirements are shown here. Metadata defines hierarchy; the issue labels array is what GitLab filters. Body requirements follow the Agile Playbook; standalone Task issues are optional.

TypeRequired metadataBody / acceptance contentParent rule
THEMEtype, id, state, status, areaPurpose, portfolio outcome, success measures, constraints, review cadenceRoot; no parent
EPICtype, id, theme, state, areaOutcome statement, target window, success picture, risksTheme ID in parent (Cascade convention)
FEATUREtype, id, parent, theme, state, area, effortShort description, PfW/DWI reference, Feature Done-When, dependenciesEpic ID
STORYtype, id, parent, theme, state, area, points, sprintUser story, observable acceptance criteria, constraints, Definition of DoneFeature ID
TASKtype, id, parent, theme, state, area (example convention)Objective, steps, verification, evidence and constraintsStory ID; prefer an embedded Story checklist normally
GitLab's native Epics and Work Items may be stored and related differently from Cascade's conceptual model. This example illustrates Cascade's metadata convention, not a claim that web.git.mil supports every native hierarchy feature.

Data handling
The UI runs in a local browser but reads Git.mil remotely through the approved PowerShell/ARC backend. It is served locally and has no external JavaScript, CSS, or analytics dependencies. Imported data stays in this browser session unless exported.

Operating boundaries
Enabled: local scans, issue reconciliation preview, triage decisions, evidence inspection, report export.
Not enabled in the GUI: autonomous production writes, story closure, time tracking, unattended scheduling, or AI-generated semantic classification. Those require additional engineering and approved infrastructure.
